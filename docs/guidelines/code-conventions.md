# Code conventions

## Comments

- Code has no comments. Names, types and small functions carry the meaning instead.
- Claude adds a comment only when the owner explicitly asks for one.
- Comments generated by scaffolding tools are removed when the code is added. Generated files that are not edited by hand (for example `worker-configuration.d.ts`) are left as generated.
- Documentation belongs in `docs/`, not in code comments.

## Formatting and linting

- Text files use `LF` line endings on every operating system. [`.gitattributes`](../../.gitattributes) makes Git store and check them out with `LF` (Windows scripts such as `.bat`, `.cmd` and `.ps1` keep `CRLF`) and marks images, fonts and archives as binary, [`.editorconfig`](../../.editorconfig) sets `end_of_line = lf` for editors, and Prettier uses `endOfLine: 'lf'`. A new binary file type gets a `binary` line in `.gitattributes`.
- Prettier has one config for the whole repository: [`prettier.config.js`](../../prettier.config.js) at the root. Packages do not add their own.
- ESLint rules shared by all packages live in [`eslint.config.base.js`](../../eslint.config.base.js) at the root. Each package has a short `eslint.config.js` that imports the base and adds only what is specific to it, for example the Storybook rules in `packages/ui`.
- Stylelint has one config for the whole repository: [`stylelint.config.js`](../../stylelint.config.js) at the root. It checks `.css` files and `<style>` blocks in `.svelte` files from each package's `lint` script.
- Stylelint requires a design token (`var(--…)`) for colours, margins, paddings, gaps, font sizes, weights, line heights, letter spacing, border widths and radii, and forbids literal colours and lengths in the `background`, `border*`, `outline` and `box-shadow` shorthands. `0`, `auto`, `none`, `transparent`, `currentColor`, inherited keywords and a unitless line height of `1` are allowed, and so is any value that contains a `var(--…)`, such as a `calc()` over tokens.
- Stylelint also forbids `!important`, duplicate properties and selectors, unknown properties and units, named colours, `box-shadow` and `text-shadow`, and a `min-width` media query with any value other than `768px`.
- Palette tokens (`--color-neutral-*`, `--color-red-*`, `--color-amber-*`, `--color-green-*`) may appear only in `packages/ui/src/lib/styles`; everywhere else Stylelint reports them.
- A literal that belongs to one component and has no shared role (see [ui-patterns.md](ui-patterns.md#tokens)) is the only reason to disable a rule, and it needs the owner's agreement.
- The lint dependencies used by the shared configs are root dev dependencies.

## TypeScript and Svelte

- Functions declare their return type. Inline callbacks and functions assigned to a typed variable may rely on inference (ESLint `@typescript-eslint/explicit-function-return-type`).
- A fixed set of values is a string literal union type, for example `'one' | 'few' | 'many'`, not a TypeScript `enum`.
- Attributes of Svelte elements and components are kept in a fixed order by ESLint `svelte/sort-attributes`: identity (`this`, `id`, `name`) first, then `style` and `class`, then all other attributes and props alphabetically (event handlers such as `onclick` included), then `bind:` directives, then directives such as `use:` and `transition:`. `pnpm exec eslint --fix` sorts them.
- A CSS animation is one full `animation` shorthand that names its keyframes, for example `animation: fade 5.6s linear infinite`. The production CSS minifier turns a shorthand without a name into `animation: none`, so a name set by another rule runs for 0 s and only the build shows it. `packages/ui/src/lib/components/animations/animations.test.ts` checks the library components.
- Svelte scopes every selector of a component's `<style>` to the component's own elements, also inside `:has()`. A selector in `:has()` that must match an element rendered by a child component or a snippet is wrapped in `:global(...)`, for example `.tooltip:has(:global(:focus-visible))`; without it the rule silently never applies, so it needs a browser test.
- An effect reacts to everything it reads. When a state object is replaced as a whole (`form = { ...form, ... }`), an effect meant to react to one field reads it through a primitive `$derived`, for example `let query = $derived(form.name.trim())`, or it re-runs on every replacement.
- Costly work (layout, sorting, measuring) is derived from primitive `$derived` values, not from an object that is recreated on every frame or pointer move. A primitive derived notifies its dependents only when its value changes, so a pan or an animation frame recomputes only what really moves.
- Markup has no wrapper elements without a purpose. Prefer a semantic element (`footer`, `section`, `nav`) to a `div` when one fits.
- `pnpm lint` checks the Markdown of the whole repository with Prettier, then runs Prettier, ESLint and Stylelint inside each pnpm package, so code outside them (for example a future Go backend) is not touched and uses its own language tooling.

## Svelte markup

- When a component tag spans several lines, its text content goes on its own line. Text directly after `>` makes Prettier break the tag in odd places.

```svelte
<Alert title={m.signIn.errorTitle} tone="danger">
	{formError}
</Alert>
```

## Reuse

- Before writing a mechanism, look for one that already exists in `#lib` or `packages/ui` and use or extend it, for example an option on a library component instead of a new component.
- When a change needs logic or markup that already lives elsewhere (a guard against leaving a form, a bar, image loading), it moves that code into a shared module or component in the same pull request and switches the existing callers to it; it does not copy it.
- Duplication found that the change did not introduce gets its own `Chore` issue in Linear instead of widening the pull request.
- Long reference data, such as the list of country codes, is not typed by hand: it is generated once from a trusted source (the ICU data behind `Intl.DisplayNames`, for example) by a short script, the source and the left-out entries are written in the ADR, and a test checks the number of entries and the exclusions ([ADR-0057](../decisions/0057-location-country-and-type-of-place.md)).

## Web app layout

The SvelteKit app in `apps/web/src` is organised in feature modules ([ADR-0126](../decisions/0126-organise-the-web-app-in-feature-modules-with-enforced-limits.md)). Every file in `lib` follows this layout, and `pnpm lint` keeps it that way.

| Path                           | Holds                                                                                                                                                                                                                                                                         |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `routes/`                      | Pages and layouts only (`+page.svelte`, `+layout.ts` and other SvelteKit files)                                                                                                                                                                                               |
| `lib/shared/`                  | Technical code that knows nothing about artworks: the Supabase client and generated types (`shared/data/`), form helpers (`shared/forms/`), storage, ids, search, dates                                                                                                       |
| `lib/i18n/`                    | The message dictionary                                                                                                                                                                                                                                                        |
| `lib/catalogue/`               | The domain model several modules share (artwork and value types, eras, artwork types, record numbers, years), without Supabase and without components                                                                                                                         |
| `lib/<module>/`                | One feature, named as the learner knows it: `artworks`, `images`, `wall`, `card-index`, `values` ([ADR-0127](../decisions/0127-keep-the-value-page-in-a-values-module.md)), `notes`, `pins`, `glossary`, `timeline`, `review`, `profile`, `auth`, `feedback`, `data-transfer` |
| `lib/shell/`                   | The atelier layout, the menu, the theme and the rail, which put the modules together into the app                                                                                                                                                                             |
| `lib/startup/`, `lib/testing/` | The loading screen shown before the app starts; helpers and fixtures for tests                                                                                                                                                                                                |

Inside a module (example: `wall`):

| Path                                        | Holds                                                                                                                              |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `types/wall-order.ts`                       | One exported type per file, named after the type (`WallOrder`)                                                                     |
| `wall-data/wall-data.ts`                    | Calls to Supabase; only `*-data.ts` files import the client                                                                        |
| `errors/errors.ts`                          | The module's table of error codes, passed to the shared error-message factory                                                      |
| `filter/filter.ts`, `filter/filter.spec.ts` | Domain logic (validation, mapping, layout) with its tests                                                                          |
| `period-tracker/period-tracker.svelte.ts`   | State built with runes                                                                                                             |
| `utils/years/years.ts`                      | A general helper of this module, named by its topic; helpers several modules need go to `shared/utils/`                            |
| `components/ArtworkWall/ArtworkWall.svelte` | A component, with `ArtworkWall.svelte.spec.ts` beside it; `components/` gets subfolders by screen area once it holds more than ~12 |

- Every `.ts` and `.svelte` file of code sits in a folder named like the file without its extension, together with its tests and nothing else. Imports name the file itself (`#lib/wall/filter/filter.ts`); there are no `index.ts` files. Type files in `types/`, SvelteKit files in `routes/` and `i18n/pl.ts` keep their places. `packages/ui` follows the same rule: a component sits in its own folder with its story and test (`components/Button/Button.svelte`, `Button.stories.svelte`, `Button.svelte.spec.ts`), its exported types sit one per file in `src/lib/types/`, and `src/lib/index.ts`, the package's entry, is the only `index.ts`.
- `utils/` holds general helpers only, each in a file named by its topic, never one `utils.ts`. Domain logic such as the wall filter or the grouping is not a helper and stays at the top of the module.
- Dependencies point down only: `shared` imports nothing from `lib` except `i18n`; `catalogue` imports `shared` and `i18n`; a module imports `shared`, `i18n`, `catalogue` and other modules, with no cycles; only `routes/` (and the server hook, which inlines the theme script) imports `shell`; nothing in `lib` imports `routes/`. A view component of a module therefore renders inside `AtelierLayout` from its route, never wraps itself in it.
- Code that two modules need and that is not about one of them moves down, to `catalogue` when it is about the domain and to `shared` when it is not, instead of one module importing it from the other in both directions.
- A type used by more than one file, or by views, lives in its own file in the module's `types/` folder. A type used by one file only, such as the shape of rows a query returns, stays in that file. A type derived from a value (`keyof typeof OWN_IMAGE_EXTENSIONS`) stays exported next to that value, since a types file importing it back would close a cycle.
- Components used in more than one module, or that know nothing about the app's data and routes, belong in `packages/ui` instead.
- Files in `routes/` connect pieces: they read data, call module functions and render components. Logic (Supabase calls, validation, mapping, formatting) lives in `lib/<module>`. When the script of a page grows past about 80 lines, its logic moves into a view component of its module, with a state class when the component's script would pass 200 lines, and the page keeps `load`, `snapshot`, navigation and the snippets it hands to `AtelierLayout`. The wall is the example: `routes/(app)/atelier/+page.svelte` creates a `WallView` (`wall/wall-view/wall-view.svelte.ts`) and renders `WallTools` in the bar, the filter panel, the period strip and `WallPage` inside the layout.

## Size limits

| What                                | Limit     |
| ----------------------------------- | --------- |
| A `.ts` file                        | 300 lines |
| A `.svelte` file                    | 400 lines |
| The script of a component           | 200 lines |
| The styles of a component           | 150 lines |
| A test file                         | 800 lines |
| Cyclomatic complexity of a function | 15        |

- Generated files (`database.types.ts`), the message dictionary (`i18n/pl.ts`) and long reference data (`countries.ts`) are exempt.
- A file over a limit is split along what the learner sees, not along technical layers: `ArtworkView` becomes the stage, the information panel and the pin card, not a script file and a style file. Long styles usually mean several components in one, or a style that belongs in `packages/ui`.
- A snippet passed to another component, or longer than about 30 lines, becomes a component.

- The limits live in `lint/limits.js`. What broke a rule when the check was added is listed in [`lint/allowlist.json`](../../lint/allowlist.json) by kind (`lines`, `script`, `style`, `complexity`, `route-script`, `storage`, `ui-text`, `component-test`, `component-story`, `test-keyboard`, `test-waiting`, `margin`, and `layout` by folder, which is empty). An entry that is no longer needed fails the check, so a change that fixes a file removes its entry; no change adds one without the owner's agreement.
- `dependency-cruiser` runs twice: over files, and over modules with `.dependency-cruiser-modules.cjs`, which collapses each `lib/<module>`. Its baselines, `apps/web/.dependency-cruiser-known-violations.json` (files) and `.dependency-cruiser-known-module-cycles.json` (modules), are empty: no cycle and no import in a wrong direction is left. A baseline gains no entry without the owner's agreement; one that does is regenerated with `pnpm exec depcruise src --output-type baseline` (plus `--config .dependency-cruiser-modules.cjs` for modules).

## Naming

- Svelte components: `PascalCase.svelte`, the same name they are imported under, in a `PascalCase` folder of the same name.
- A component is named for what it is, not for one way it opens or one interaction: `Popover`, not `HoverCard`, because it also opens on a click.
- Other files and folders: `kebab-case`, for example `auth-artworks.ts`. Route folders are kebab-case because they become URLs (`/forgot-password`).
- A file that calls Supabase ends in `-data.ts` (`glossary-data.ts`); a file with runes ends in `.svelte.ts`; any other `.ts` file is pure logic.
- SvelteKit files keep the framework's names (`+page.svelte`, `+layout.ts`).
- Tests: the tested file's name plus `.spec.ts`, in the tested file's folder.

## Imports

- Code in `apps/web` imports from another folder through `#lib/...` with the file extension, for example `#lib/auth/validation/validation.ts`. The alias comes from `imports` in `package.json`.
- Files in the same folder import each other with a relative path (`./errors.ts`).

## Routes and navigation

- Pages that need a signed-in learner are in the `(app)` group; the start page, sign-in, sign-up and password reset are in `(auth)`. The atelier lives at `/atelier`, one artwork at `/atelier/<record number>`, its edit form at `/atelier/<record number>/edit`, the add form at `/atelier/new`, the trash at `/atelier/trash` ([ADR-0023](../decisions/0023-atelier-routes-and-commons-thumbnails.md)), the card index at `/atelier/values`, a value page at `/atelier/values/<kind>/<id>` and its form at `/atelier/values/<kind>/<id>/edit` ([ADR-0050](../decisions/0050-store-value-pages-in-details-tables.md)); the glossary at `/atelier/glossary`, an entry at `/atelier/glossary/<id>`, its form at `/atelier/glossary/<id>/edit` and the add form at `/atelier/glossary/new` ([ADR-0074](../decisions/0074-keep-a-glossary-of-terms-with-definitions-from-wikipedia.md)); the timeline at `/atelier/timeline`, the add form of an event at `/atelier/timeline/events/new` and its edit form at `/atelier/timeline/events/<id>/edit` ([ADR-0093](../decisions/0093-show-the-collection-and-historical-events-on-a-timeline.md)); `/` is the start page. Each group's `+layout.ts` redirects by session. A page reachable in both states (for example `update-password`, opened from an email) stays outside the groups.
- Paths in code are built with `resolve()` from `$app/paths`, for example `resolve('/(auth)/sign-in')`, in views and in `redirect()` alike, so a renamed route fails the type check.
- Internal navigation follows [ui-patterns.md](ui-patterns.md#links-and-buttons): links for going somewhere, `goto` only after an action.
- A `goto` after an action that changed data (a save, a delete, moving to the trash) passes `refreshAll: true`. Links preload their page's data when they are pressed, and without it the navigation reuses data loaded before the change, so the page shows the old content until a reload.
- In SvelteKit 3 the `from` and `to` targets passed to `afterNavigate` can carry `url: null` (on the first navigation `from` is not `null` but has no URL), although the types say `URL`. Code reads them through `from?.url` and `to?.url`: an exception in an `afterNavigate` of the root layout stops the client router, and every link then reloads the whole page (ATL-253).

## UI text

- All UI text comes from the message dictionary in `lib/i18n` ([ADR-0015](../decisions/0015-typed-message-dictionaries-for-i18n.md)). Learner data and artwork titles are not UI text.
- Keys are grouped by screen or domain in camelCase (`signIn`, `forgotPassword`, `authErrors`); text shared by several screens goes in `common`; texts for `packages/ui` go in `ui`.
- A running state pairs with its action: `submit` and `submitting`, `resend` and `resending`. Alert titles end in `Title` (`errorTitle`, `sentTitle`).
- A message with values is a function (`sent(email)`). Plural forms use `plural()` with `Intl.PluralRules`.
- Adding a language takes three steps:
  1. Add a dictionary file of type `Messages` (for example `en.ts`).
  2. Choose the dictionary and `locale` in `lib/i18n/i18n.ts` from the learner's setting or `navigator.language`.
  3. Set `document.documentElement.lang` in the root layout and pass `locale` to `Intl.PluralRules` and date formatting.

## Errors from services

- Every error from Supabase or another service goes through a mapping function in `lib/<domain>/errors.ts`, which picks a dictionary message by error code and falls back to a general message. `error.message` is never shown to the learner.
- A database error is mapped by a function built with `errorMessages` from `#lib/shared/data/errors/errors.ts`, given the module's table of codes and its network message; the factory alone decides what counts as a network error. Errors of other shapes (auth, storage, Wikimedia) keep their own mapping in the module.
- Domain functions return the mapped message, so views only show it.
- A domain function that writes passes the error through `failureMessage` from `lib/auth/expired-session-data/expired-session-data.ts`: an authorization error (HTTP 401 or a `PGRST301`..`PGRST303` code) signs the learner out and returns the session-ended message; any other error goes to the domain's mapping function.

## External services

- URLs of one image source are built in one module, `lib/images/<source>/<source>.ts` (for example `commons/commons.ts`). Views and other domains call it instead of writing the URL themselves.
- The Polish Wikipedia API (the definitions of the glossary) and the Wikidata API it is checked against are called only from `lib/glossary/wikipedia/wikipedia.ts`, through the same `fetchJson` as the image sources, so the identification and the retry are shared. Tests and screenshots mock it: the cloud environment cannot reach `pl.wikipedia.org`. A local session can, so a change to how the responses are parsed (the definition, the sentences, the lead) is also checked against a handful of live articles before the pull request; sample texts written by hand miss the variety of real leads. A script that calls the app's Wikimedia functions from Node for such a check sets a `User-Agent` header naming the app and the repository URL (as `API_USER_AGENT`): browsers send one themselves, while Node's default makes Wikimedia answer `403`.
- A request to a service that asks clients to identify themselves (for example the Wikimedia `Api-User-Agent` header) names the app and the repository URL. It never carries personal data such as an email address.
- Requests to a rate-limited service are batched where the API allows it, and a 429 is retried at most once, after `Retry-After` ([ADR-0023](../decisions/0023-atelier-routes-and-commons-thumbnails.md)).
- The Query Service optimizer may start a query from a large pattern such as `?item wdt:P18 ?image` instead of from the few results of `SERVICE wikibase:mwapi`, and then times out after about 60 s with a `502` or `504`. A query that joins search results under `UNION` with other patterns starts with `hint:Query hint:optimizer "None".`, so it runs in the written order, searches first (ATL-213).
- A request to a Wikimedia service gives up after 30 s (`AbortSignal.timeout` in `fetchWithRetry`), is not retried, and reports a `504`, which the learner sees as the "did not answer" message rather than a network error.
- A SPARQL query to the Wikidata Query Service never follows a subclass path such as `wdt:P31/wdt:P279*`: it runs for tens of seconds and times out. Narrow the results with `FILTER EXISTS` and `FILTER NOT EXISTS` on specific properties and classes instead.

## Database

- Every table in `public` has Row Level Security on, policies for `authenticated` only, and an explicit `revoke all ... from anon, authenticated` followed by the narrowest `grant` (columns, not whole tables, for writes). Supabase grants new objects to the API roles by default, so a migration that skips the `revoke` exposes the table.
- Functions are `security invoker` with `set search_path = ''` and, when callable from the app, `revoke all ... from public, anon` plus `grant execute ... to authenticated`. A `security definer` function lives in the `private` schema and is not granted to the API roles.
- Uploaded files sit under a folder named after the owner's id, and the Storage policies compare that folder with `auth.uid()`.
- `supabase/tests/security.sql` runs in the `migrations` job against the replayed migrations. It checks the rules above for every table and function, and that one learner cannot read or change another's rows or images. A new table, function or policy extends it.
- `supabase/tests/review-session.sql` runs in the same job and checks the rules of `review_session` on a learner's own artworks, for example which artwork gets a quiz. A change to a session rule extends it. `review-streak.sql`, `notes-mentions.sql`, `artwork-images.sql` and `artwork-fields.sql` do the same for `review_streak`, `notes_mentions`, the other images of `save_artwork` and the learner's own artwork fields.
- A migration that changes the rules of a function comes with a test in `supabase/tests/` that fails against the previous version of the function and passes with the new one. Check both on the local stack before pushing.
- The message of an assertion in `supabase/tests/` names the failure, not the state the assertion checks: `assert count = 2, 'save_artwork drops the entries it was not given'`. A reviewer reads it as the bug that would show if the assertion failed.

## Tests

- Unit tests (Vitest) cover every module with logic: validation, mapping, formatting and the domain functions that wrap Supabase (with the client mocked).
- Coverage may not fall below the thresholds in `coverage.thresholds` of each package's `vite.config.ts`. When a change lifts a whole percent above a threshold, CI asks to raise it in the same change, so the thresholds only go up.
- Components and pages have component tests named `<Name>.svelte.spec.ts` next to the component (for a route, `page.svelte.spec.ts` next to `+page.svelte`). They run in Chromium with Vitest browser mode; other tests run in Node ([ADR-0018](../decisions/0018-component-tests-in-vitest-browser-mode.md)).
- Test names describe behaviour in a sentence ("rejects a short password and says how long it is").
- Expected texts are read from `m`, and in `packages/ui` from `defaultUiMessages`. A literal string is used only when the text itself is under test, for example a plural form.
- The app's browser tests see the Polish library texts: `src/lib/testing/ui-messages/ui-messages.ts`, the `setupFiles` entry of the `client` project, calls `setUiMessages(m.ui)` ([ADR-0087](../decisions/0087-set-library-texts-once-for-the-whole-app.md)). A library text is read from `m.ui`, for example `m.ui.valueField.remove('barok')`. Library styles are not loaded in tests, so a custom checkbox has no size: click its label.
- A test of a size or position loads the styles itself. In `packages/ui`, `src/lib/testing/control-height.ts` loads them and gives the token's height (`controlHeight`) and the height of a control's outlined box (`outlinedHeight`); in the app, the spec imports `@study-atelier/ui/styles.css`. Such a test may reach that box by its class.
- A test of a library text override renders the component through `src/lib/testing/MessagesHost.svelte` in `packages/ui`, which calls `setUiMessages` before it renders the component and puts the previous texts back when it is destroyed.
- Component tests find elements the way a learner does: by role, label and visible text from `m`, not by component internals, so a refactor that keeps the behaviour keeps the tests green.
- A test enters a whole value with `fill()` and presses only the keys it needs (`{Enter}`), instead of typing text with `userEvent.keyboard`: every key is a separate round trip to the browser, and under the load of a full local run such tests come close to the 15 s timeout (ATL-151). Typing key by key is kept for behaviour that depends on it, such as the notes editor.
- A test of behaviour that depends on time (a message that disappears, a delay) uses fake timers and advances them with `vi.advanceTimersByTime`; it never waits for real time, which makes tests slow and unstable in CI. In browser mode fake only what the code uses, for example `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout', 'Date'] })`, so `expect.element` can still poll.
- The content of a closed `details` is not in the accessibility tree: a test opens it by clicking its `summary`, and checks that such content is absent with `not.toBeInTheDocument()`, not `not.toBeVisible()`.
- A hidden `input type="file"` has no role, so a test reaches it with `document.querySelector('input[type="file"]')` and picks a small file with `userEvent.upload`. A large file (for example one over the upload limit) is built in the page and set on the input with a `DataTransfer` and a `change` event, because `userEvent.upload` sends every byte from Node to the browser and takes seconds. This and the outlined box of a size test are the only exceptions to finding elements by role.
- Code that loads an image with `new Image()` (for example to read its size) is tested with a stub: `vi.stubGlobal('Image', ...)` with a class that calls `onload` or `onerror`, and `vi.unstubAllGlobals()` after each test. When the order of events matters, the stub keeps `onload` and the test calls it at the chosen moment. A real image for a page test is drawn on an `OffscreenCanvas` and turned into a `File`.
- The wall lays its tiles out column by column, so the order of the tile links in the DOM is not the order of the wall. A test of the wall's order reads the remembered wall sequence (`study-atelier:wall-sequence` in `sessionStorage`) instead of the links.
- Supabase is never called from tests. A test mocks `#lib/shared/data/supabase/supabase.ts` with `vi.mock` and returns results built with the helpers in `src/lib/testing/`, which use the real Supabase error classes. Navigation (`$app/navigation`) is mocked the same way, so page tests never run the real router: code in `afterNavigate`, the root layout or anything else that touches the router is also checked in a real browser with `pnpm screenshot --steps` ([cloud-sessions.md](cloud-sessions.md)), clicking through the flow and reading the result, before the pull request.
- A test that clicks a back link or an arrow that goes back through the history spies on `history.go` (`vi.spyOn(history, 'go').mockImplementation(() => {})`), which `goBackThroughHistory` calls. An unmocked history navigation takes the test page away, and Vitest ends the file with "Browser connection was closed", which looks like a lack of resources but is not.
- Test data that is not UI text (addresses, passwords, sample titles) is made up, in English, and never real personal data, for example `learner@example.com`.
